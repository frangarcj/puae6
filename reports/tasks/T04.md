# T04 — contrato y arnes, no emulacion

- `bridge/include/p6.h` fija ABI nativa v1 para una instancia, A500
  Chip512K/Slow512K, buffers prestados, errores acotados y avance por boundary.
  Los probes C11/C++17 verifican layout nativo de 64 bits y enlace C. No hay
  implementacion del motor ni prueba ABI C#/Waterbox.
- `tools/scenario_schema.py` valida el esquema v1 y la telemetria completa de
  salida: campos/tipos/rangos, eventos ordenados, limites de RAM, identidad y
  todos los boundaries. Validar un JSON no autentica ni ejecuta su productor.
- `tests/fixtures/counter68k` contiene un programa original MIT y un ensamblador
  deliberadamente limitado a sus instrucciones. Fuente, ensamblador y salida
  estan fijados por SHA-256. Es un programa RAM de seis bytes para un futuro
  harness CPU, no una ROM de arranque. No se ha ejecutado en WinUAE.

Comando implementado:

    python3 tools/check.py --check HARNESS01 --task T04

Ejecuta las cuatro suites declaradas (contrato nativo, esquema, fixture y
propio dispatcher), exige pruebas presentes y sin skips/xfails, e informa JSON
con assertion_set/assertions_executed y evidence=HARNESS. El unico exit code
cero es PASS; FAIL=1, BLOCKED=2 y NOT_IMPLEMENTED=3. --require permite exigir
assertions adicionales, nunca omitir las basicas. Otro task/profile no hereda
esta cobertura. Los mocks de los tests prueban el transporte del dispatcher;
no se registran como evidencia de emulacion.

    python3 tools/check.py --check STEP01 --scenario tests/scenarios/counter68k.json

Este segundo comando DEBE devolver NOT_IMPLEMENTED y exit 3: valida el JSON,
pero aun no hay runner del motor. Tampoco HARNESS01 con --scenario puede dar
PASS de ese escenario. Un ID desconocido o escenario malformado devuelve FAIL.
Los checks anteriores de importacion/codegen conservan sus comandos propios;
no se anuncian aqui como assertions integradas de otras puertas.
