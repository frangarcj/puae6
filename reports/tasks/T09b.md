# T09b BLOCKED: lowering TLS de Clang/LTO

El harness net8.0 compila sin warnings con SDK 10.0.400 y se ejecuta con runtime
10.0.11 mediante RollForward=Major. Carga el ELF y dylib nuevos verificados por
hash. Constructor C++ y allocations iniciales se ejecutan dentro de Waterbox.
Todavia NO hay PASS de frame, snapshot, nueva instancia ni WB01/WB15.

Dos intentos locales:

1. thread_local normal: SIGSEGV en smoke_init, PC 0x36f00018204, guardando a
   0x1014 tras leer TPIDR_EL0. El musl fijado exige el TLS indirecto desde x28.
2. CXXFLAGS=-femulated-tls y compiler-rt emutls 18.1.8 fijado/enlazado:
   SIGSEGV equivalente, PC 0x36f0001b4b8, direccion 0x1012. El ELF LTO no contiene
   __emutls_get_address y sigue usando TLS directo. El probe sin LTO del agente
   produce correctamente la llamada a __emutls_get_address.

Caso conservado: build/waterbox/tls-repro contiene ambos ELF, recibos SHA-256,
logs y Makefiles, mas guest.cpp. build/waterbox/tls-audit contiene el probe
aislado del lowering sin LTO. No se han retocado sysroot ni fuentes MacHawk.

Reproduccion actual (se espera fallo, no una puerta aprobada):

```sh
python3 tools/build_waterbox.py --snapshot-smoke
```

Hipotesis verificables para retomar:

- El backend LTO no recibe -femulated-tls: common.mak enlaza usando CCFLAGS,
  mientras el cambio solo entra en CXXFLAGS. Comparar bitcode, comando de enlace
  y ELF final exigiendo descriptor/emutls y ausencia de TLS directo en el probe.
- Una diferencia LLVM22/toolchain18 o resolucion del simbolo weak elimina el
  lowering/objeto; comparar el mismo probe con y sin LTO usando identicos inputs.

Decision y fuente: docs/adr/waterbox-compiler-tls.md. No quitar thread_local,
no cambiarlo por un global y no presentar el build como prueba de snapshot.
Se pasa a T05, independiente, conforme al limite de intentos de AGENTS.md.
