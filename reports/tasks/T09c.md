# T09c: callbacks ARM64 y paginas logicas/fisicas en Waterbox real

Todo lo de abajo esta medido con el runtime Darwin ARM64 de MacHawk (dylib compilada
por build_waterbox.py) y el harness managed; es evidencia SMOKE_RUNTIME, no Amiga.
Reproduccion: `python3 tools/build_waterbox.py --smoke` (exige WB01, WB13, WB14, WB15
completos y WB16 en el build; un hueco de cobertura falla la receta).

## WB13: callbacks

El guest cruza un callback del host (`wbx_get_callback_addr`) con canarios en x19-x27 y
d8-d15 y comprueba x18, x28, x29, sp, argumentos, retorno, un valor de pthread_key y errno.
Todo se conserva: en el mismo sandbox, tras un restore, en un sandbox nuevo y con un
callback que reentra en el guest (usa la pila alternativa). x18 vale 0 y es estable; cada
sandbox tiene su propio x28 y el mismo sandbox conserva el suyo tras restaurar.

## WB14: dirty tracking por grupo de 16 KiB

- Una sola escritura en una pagina logica de un grupo limpio marca las CUATRO paginas
  logicas como dirty, para cada una de las cuatro paginas; no cambia ninguna pagina fuera del
  grupo. El coste de una escritura es el del grupo entero (relevante para T33/T36).
- Restaurar un snapshot tomado con el grupo limpio devuelve las cuatro paginas a su
  contenido, incluida la que se escribio, y deja el grupo limpio (las cuatro coinciden).
  Una segunda mutacion tras el restore tambien se deshace: el seguimiento se rearma.
- El bit dirty es respecto a la linea base del seal, no "desde el ultimo restore": lo que
  `init` escribio antes del seal es linea base y el grupo de RAM sale limpio.
- El guest rechaza pagina 4, offset 4096 y buffer desconocido sin escribir nada.

## WB15: identidad

El harness verifica los hashes de guest y dylib contra el recibo, restaura el snapshot en un
PROCESO nuevo (otro pid, mismos hashes) y pasa el oraculo analitico. Un recibo con otro hash o
que apunta a un ELF x86_64 falla con "guest artifact identity", sin fallback.

## Hallazgo: el runtime NO rechaza protecciones ni arquitectura incompatibles

Cargas dañadas del guest real, cada una en un proceso hijo (`load_probes` en
build/waterbox/smoke-result.json):

| Carga | Runtime |
|---|---|
| magic inválido, ELF truncado | error limpio |
| `e_machine` = x86_64 | ACEPTA (un guest de otra arquitectura carga y solo falla al ejecutar) |
| heap sealed de 4096 (no multiple de 16 KiB) | ACEPTA |
| pagina RW dentro de un grupo RX | ABORTA el proceso (SIGABRT, "non-unwinding panic") |

DARWIN_ARM64.md dice que las protecciones incompatibles en un grupo "son un error"; en el
runtime es un aborto, no un error devuelto, y arquitectura y layout no se validan. Por eso la
garantia esta en el build y el harness: `validate_elf` rechaza las cuatro imagenes dañadas (la
receta lo comprueba sobre los ficheros que el harness escribe en build/waterbox/damaged) y la
identidad por hash impide cargar otro guest. La receta tambien falla si el runtime llegara a
ACEPTAR el grupo mixto. No se ha tocado MacHawk ni su runtime.
