# T05d2b2v — vistas y duplicados zfile

fopen_parent valida offset/tamaño contra el origen y el root antes de crear una
vista. Aplana la cadena y retiene una referencia del root; el cierre del origen
o una vista intermedia no invalida las restantes. La vista tiene cursor propio
y sus lecturas avanzan tambien el cursor del root, como upstream. Rechaza
escritura, truncado y acceso directo al buffer. Un root RAM puede crecer sin
dejar un puntero antiguo en las vistas; truncarlo produce lectura corta/error
acotado, no una lectura fuera del nuevo tamaño. Una vista conserva su extensión
de creación. Nuevas vistas sobre una región ya truncada se rechazan.

dup de RAM copia los bytes, cursor y metadata; conserva allocsize=0 como upstream
(fwrite denegado). dup de un asset abre un cursor independiente sobre los bytes
registrados, sin FILE ni host. dup de una vista vuelve a referenciar su region
en el root y empieza en cero, como la rama useparent de 6030. Los errores de
asignacion no publican objetos a medio crear ni incrementan referencias.

La lista y opencnt usan el layout original. Cada open/dup/vista exitoso requiere
un close; cerrar dos veces la misma referencia no es un contrato valido. exit
libera todas las referencias restantes y admite repeticion. No se expande la
API para compartir handles entre hilos ni para serializacion nativa.

Pruebas sobre zfile.cpp real materializado: ASan/UBSan, padres RAM y blobs,
cierre padre/hijo en ambos ordenes, vistas anidadas, cursor y EOF por elementos,
canarios, rangos extremos y overflow, crecimiento/truncado del root, independencia
de duplicados, contador de referencias saturado e invalidacion de blobs. El
allocator inyectado comprueba fallo en cada reserva y cero allocations vivas tras
exit; fallar repetidamente un dup de asset tampoco agota sus handles.

Suite completa: 113 tests pasan. Tras la revision Luna se validan tambien los
81 bytes del nombre original mutable (sin NUL o UTF-8 invalido da error antes
de copiar) y se satura la suma de capacidad antes de sumar, evitando overflow
con size_t de 32 bits. Las cuatro pruebas zfile vuelven a pasar tras esos cambios;
no se afirma haber ejecutado un build de 32 bits. HOST01 inventario y HARNESS01
T04 pasan, al igual que git diff --check y validacion documental del plan.
